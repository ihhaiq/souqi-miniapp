# Souqi Mini App — Frontend Handoff

هذا المستودع يحتوي **الفرونت إند فقط** لتطبيق Souqi Mini App على تليكرام.

الغرض من هذه النسخة هو تسليم واجهة جاهزة لمطور الباك إند بحيث لا يحتاج إلى إعادة بناء التصميم أو فهم ملف HTML ضخم واحد. الواجهة الحالية تعمل بوضع معاينة مستقل، وتم تجهيز طبقة واضحة لربطها بأي Backend مناسب.

> مهم: هذا المشروع لا يحتوي Bot Token، مفاتيح API سرية، بيانات قاعدة بيانات، منطق دفع حقيقي، أو مصادقة موثوقة على جهة العميل. كل هذه الأشياء مسؤولية الباك إند.

---

## 1. حدود المسؤولية

### Frontend — موجود في هذا المستودع

الفرونت إند مسؤول عن:

- عرض تصميم المتجر.
- قراءة بيانات المستخدم البصرية المتاحة من Telegram WebApp.
- عرض الرصيد القادم من الباك إند.
- عرض عناصر السوق حسب الفئة.
- البحث والترتيب والفلاتر محليًا على البيانات المستلمة.
- إرسال طلب شراء عنصر.
- إرسال طلب بدء تعبئة المحفظة.
- إرسال `Telegram.WebApp.initData` مع طلبات الـ API حتى يتحقق منها السيرفر.
- عرض حالات التفاعل الأساسية للمستخدم.

### Backend — مطلوب من المطور المستلم

الباك إند مسؤول عن:

- التحقق من `Telegram.WebApp.initData` على السيرفر.
- تحديد هوية المستخدم وصلاحياته.
- إدارة قاعدة البيانات.
- الرصيد الحقيقي.
- الكتالوج الحقيقي والأسعار والمخزون.
- إنشاء الطلبات.
- عمليات الدفع والتعبئة.
- التحقق من السعر والكمية والعنصر مرة ثانية على السيرفر.
- منع التلاعب وإعادة الطلبات والطلبات غير الصالحة.
- تسجيل العمليات والأخطاء.
- سياسات CORS.
- أي Bot Token أو Secret أو مفتاح دفع.

**لا تعتمد على أي قيمة حساسة قادمة من JavaScript باعتبارها حقيقة موثوقة.**

## 2. هيكل المشروع

```text
souqi-miniapp/
├── index.html
├── index.htm
├── config.js
├── README.md
├── css/
│   └── styles.css
├── js/
│   ├── api.js
│   └── app.js
└── Assets/
    └── ...
```

| الملف | المسؤولية |
|---|---|
| `index.html` | نقطة الدخول الأساسية للـ Mini App وبنية عناصر الصفحة |
| `index.htm` | ملف توافق قديم يحول تلقائيًا إلى `index.html` |
| `css/styles.css` | كل تنسيقات وتصميم الواجهة |
| `js/app.js` | حالة الواجهة، العرض، البحث، الفلاتر، Telegram UI والتفاعلات |
| `js/api.js` | طبقة الاتصال الوحيدة المخصصة حاليًا للباك إند |
| `config.js` | رابط الـ API، وضع Demo، المهلة وأسماء Endpoints |
| `Assets/` | صور وأصول الواجهة |

ترتيب تحميل JavaScript داخل `index.html` هو:

```text
config.js
   ↓
js/api.js
   ↓
js/app.js
```

يجب المحافظة على هذا الترتيب لأن `api.js` يعتمد على `SOUQI_CONFIG` و`app.js` يعتمد على `SouqiAPI`.

## 3. تشغيل الواجهة الحالية بدون Backend

الإعداد الافتراضي داخل `config.js`:

```js
window.SOUQI_CONFIG = Object.freeze({
  apiBaseUrl: "",
  demoMode: true,
  requestTimeoutMs: 12000,
  endpoints: Object.freeze({
    bootstrap: "/api/bootstrap",
    catalog: "/api/catalog",
    orders: "/api/orders",
    topup: "/api/wallet/topup"
  })
});
```

عندما تكون:

```js
demoMode: true
```

لا يتم طلب Backend عند بدء التطبيق، وتستخدم الواجهة بيانات المعاينة الموجودة حاليًا داخل `js/app.js`.

هذا الوضع مخصص للتصميم والتجربة فقط.

---

## 4. تفعيل الباك إند

بعد تجهيز الخادم، عدّل فقط `config.js`:

```js
window.SOUQI_CONFIG = Object.freeze({
  apiBaseUrl: "https://api.example.com",
  demoMode: false,
  requestTimeoutMs: 12000,
  endpoints: Object.freeze({
    bootstrap: "/api/bootstrap",
    catalog: "/api/catalog",
    orders: "/api/orders",
    topup: "/api/wallet/topup"
  })
});
```

لا تضف Slash أخير إلى `apiBaseUrl` إلا إذا كنت تعرف تأثيره؛ طبقة الـ API تقوم أصلًا بإزالة الـ slash الأخير.

يمكن تغيير مسارات الـ endpoints من `config.js` بدون تعديل `js/api.js`.

---

## 5. تدفق تشغيل التطبيق

عندما يكون `demoMode: false` يتم تشغيل `hydrateFromBackend()`.

الواجهة ترسل الطلبات التالية بالتوازي:

```text
GET /api/bootstrap

GET /api/catalog?category=gifts
GET /api/catalog?category=avatars
GET /api/catalog?category=collectibles
GET /api/catalog?category=channels
```

التنفيذ الحالي يستخدم `Promise.all`، لذلك فشل أحد طلبات البداية يؤدي إلى فشل عملية الـ bootstrap المجمعة ويتم تسجيل الخطأ في Console.

بيانات المعاينة الموجودة مسبقًا داخل الواجهة تبقى موجودة إذا فشل التحميل. إذا كان المطلوب في الإنتاج عدم عرض أي بيانات تجريبية عند فشل الخادم، فيفضل لاحقًا إضافة Loading/Error state صريح في `js/app.js`.

## 6. Telegram Mini App

يتم تحميل مكتبة Telegram الرسمية داخل `index.html`:

```html
<script src="https://telegram.org/js/telegram-web-app.js"></script>
```

وعند فتح التطبيق داخل Telegram، الواجهة تنفذ قدر الإمكان:

```js
tg.ready();
tg.expand();
tg.setHeaderColor(...);
tg.setBackgroundColor(...);
tg.setBottomBarColor(...);
```

تستخدم الواجهة `initDataUnsafe.user` فقط لأغراض واجهة غير حساسة مثل:

```text
photo_url
first_name
username
```

**لا تستخدم `initDataUnsafe` لإثبات هوية المستخدم على الباك إند.**

---

## 7. مصادقة Telegram بين Frontend وBackend

`js/api.js` يقرأ:

```js
Telegram.WebApp.initData
```

ثم يرسله مع كل طلب API داخل الهيدر:

```http
X-Telegram-Init-Data: <Telegram.WebApp.initData>
```

على الخادم يجب:

1. قراءة قيمة `X-Telegram-Init-Data`.
2. التحقق من توقيعها بالطريقة الرسمية الخاصة بـ Telegram Mini Apps.
3. التحقق من صلاحية `auth_date` حسب سياسة المشروع.
4. استخراج المستخدم من البيانات **بعد نجاح التحقق فقط**.
5. ربط الطلب بذلك المستخدم داخل قاعدة البيانات.

إذا فشل التحقق يجب إرجاع `401 Unauthorized` أو `403 Forbidden` وعدم تنفيذ العملية.

لا ترسل Bot Token إلى المتصفح لأي سبب.

---

## 8. شكل طلبات HTTP

طبقة `js/api.js` ترسل افتراضيًا:

```http
Accept: application/json
Content-Type: application/json
X-Telegram-Init-Data: <initData>
```

وتستخدم:

```js
credentials: "omit"
```

أي أن التصميم الحالي **لا يعتمد على Cookies أو Session Cookies**.

إذا أراد مطور الباك إند استخدام Cookies بدل هذا النموذج، يجب تعديل `js/api.js` وسياسة CORS بما يتوافق معه.

المهلة الافتراضية لكل طلب:

```text
12000 ms
```

بعدها يتم إلغاء الطلب بواسطة `AbortController`.

---

## 9. CORS

إذا كان الفرونت إند والباك إند على نطاقين مختلفين، يجب على الخادم السماح بأصل الاستضافة الفعلي للـ Mini App.

يجب أن تسمح سياسة CORS على الأقل بما يحتاجه المشروع الحالي:

```text
Methods:
GET
POST
OPTIONS

Headers:
Content-Type
Accept
X-Telegram-Init-Data
```

في الإنتاج يفضل السماح فقط بدومين الفرونت إند الحقيقي بدل `*` متى كان ذلك ممكنًا.

# API Contract

## 10. GET /api/bootstrap

### الغرض

إرجاع بيانات المستخدم الأولية المطلوبة عند فتح التطبيق.

### الطلب

```http
GET /api/bootstrap
X-Telegram-Init-Data: ...
```

### الحد الأدنى للاستجابة الحالية

```json
{
  "balance": 2007
}
```

`balance` يجب أن يكون رقمًا صالحًا.

الواجهة تعرضه في أعلى المتجر وداخل صفحة المحفظة.

يمكن توسيع الاستجابة مستقبلًا بمعلومات أخرى بدون كسر الفرونت إند الحالي، لأن الكود الحالي يهتم أساسًا بحقل `balance`.

---

## 11. GET /api/catalog

### الغرض

إرجاع عناصر السوق حسب الفئة.

### الفئات المستخدمة حاليًا

```text
gifts
avatars
collectibles
channels
```

### مثال

```http
GET /api/catalog?category=gifts
X-Telegram-Init-Data: ...
```

### الاستجابة المقبولة — الشكل المفضل

```json
{
  "items": [
    {
      "id": "#GIFT-1201",
      "name": "هدية كلاسيكية",
      "price": 3.76,
      "type": "gift"
    }
  ]
}
```

الواجهة تقبل أيضًا مصفوفة مباشرة:

```json
[
  {
    "id": "#GIFT-1201",
    "name": "هدية كلاسيكية",
    "price": 3.76,
    "type": "gift"
  }
]
```

### الحقول التي تستخدمها الواجهة

| الحقل | النوع | مطلوب | الاستخدام |
|---|---|---:|---|
| `id` | string | نعم | معرف العنصر والطلب |
| `name` | string | نعم | الاسم الظاهر والبحث |
| `price` | number | نعم | السعر والعرض والترتيب |
| `type` | string | يفضل | نوع العنصر والفلاتر |

العناصر التي لا تحتوي `id` أو `name` صالحين، أو يكون `price` فيها رقمًا غير صالح، يتم استبعادها بواسطة `normalizeItems()`.

### الأنواع الحالية المتوقعة

```text
gift
nft
character
collectible
channel
```

---

## 12. POST /api/orders

### الغرض

إنشاء طلب شراء للعنصر الذي اختاره المستخدم.

### Body الحالي

```json
{
  "itemId": "#GIFT-1201",
  "category": "gifts"
}
```

### ملاحظة أمنية مهمة

الفرونت إند **لا يرسل السعر كقيمة يعتمد عليها الخادم**.

وهذا مقصود.

على الخادم استخدام `itemId` لاسترجاع العنصر الحقيقي من قاعدة البيانات ثم التحقق من:

```text
وجود العنصر
حالته
توفره
السعر الحالي
صلاحية المستخدم
الرصيد أو حالة الدفع
عدم تكرار العملية إن كانت حساسة
```

لا تعتمد على سعر ظاهر في DOM أو JavaScript.

### استجابة مقترحة

الواجهة الحالية لا تفرض Schema محددًا لنجاح الطلب؛ أي استجابة ناجحة 2xx يتم تمريرها كما هي داخل حدث `souqi:purchase-created`.

شكل مناسب للمستقبل:

```json
{
  "ok": true,
  "orderId": "ord_12345",
  "status": "pending"
}
```

وإذا احتاج التدفق رابط دفع:

```json
{
  "ok": true,
  "orderId": "ord_12345",
  "status": "payment_required",
  "paymentUrl": "https://..."
}
```

لكن استخدام `paymentUrl` داخل الواجهة يحتاج إضافة منطق مناسب في `js/app.js`.

---

## 13. POST /api/wallet/topup

### الغرض

بدء طلب تعبئة المحفظة.

### Body الحالي

```json
{
  "amount": 50
}
```

القيمة تأتي من اختيار المستخدم في الواجهة.

**يجب التحقق منها على السيرفر** وعدم الوثوق بأنها ضمن الحدود أو القيم المسموحة.

### استجابة مقترحة

```json
{
  "ok": true,
  "topupId": "topup_12345",
  "status": "pending"
}
```

وإذا تم إنشاء رابط دفع:

```json
{
  "ok": true,
  "topupId": "topup_12345",
  "status": "payment_required",
  "paymentUrl": "https://..."
}
```

الواجهة الحالية تمرر الاستجابة داخل `souqi:topup-created` ولا تفتح رابط الدفع تلقائيًا بعد.

## 14. أخطاء الـ API

`js/api.js` يعتبر أي Status خارج نطاق 2xx خطأ.

الخطأ الداخلي يحتوي:

```js
error.status
error.payload
```

يفضل أن يعيد الخادم JSON موحدًا مثل:

```json
{
  "ok": false,
  "error": {
    "code": "INSUFFICIENT_BALANCE",
    "message": "Insufficient balance"
  }
}
```

Statuses مناسبة عادةً:

| Status | المعنى |
|---:|---|
| `400` | طلب غير صالح |
| `401` | initData غير موجود أو غير صالح |
| `403` | المستخدم غير مسموح له بالعملية |
| `404` | العنصر غير موجود |
| `409` | تعارض، تغير حالة العنصر أو نفد |
| `422` | قيمة أو بيانات غير مقبولة |
| `429` | Rate limit |
| `500` | خطأ داخلي في الخادم |

في عمليات الشراء والتعبئة، الفرونت إند الحالي يعرض رسالة عامة للمستخدم ويسجل التفاصيل في Console.

## 15. Frontend Events

إضافة إلى استدعاء الـ API، `js/app.js` يطلق Custom Events على `window`.

### قبل إنشاء طلب شراء

```text
souqi:purchase-request
```

`event.detail`:

```js
{
  item: { id, name, price, type },
  category: "gifts"
}
```

### بعد نجاح إنشاء طلب شراء

```text
souqi:purchase-created
```

`event.detail` يحتوي استجابة الخادم كما هي.

### قبل طلب التعبئة

```text
souqi:topup-request
```

```js
{
  amount: 50
}
```

### بعد نجاح طلب التعبئة

```text
souqi:topup-created
```

`event.detail` يحتوي استجابة الخادم كما هي.

مثال:

```js
window.addEventListener("souqi:purchase-created", function (event) {
  console.log("Order response:", event.detail);
});
```

يمكن استعمال هذه الأحداث لإضافة تدفقات لاحقة بدون خلط طبقة العرض بطبقة الـ API.

## 16. أين توجد بيانات المعاينة؟

البيانات الوهمية الحالية موجودة داخل:

```text
js/app.js
```

وتشمل حاليًا عناصر هدايا وقنوات وغيرها للاستخدام البصري.

عند `demoMode: false` يتم استبدال مصفوفات العرض بالبيانات القادمة من الـ API إذا نجح التحميل.

هذه البيانات ليست قاعدة بيانات ولا يجب تحويلها إلى مصدر إنتاج.

---

## 17. البحث والترتيب والفلاتر

الواجهة الحالية تقوم بالبحث والترتيب والفلاتر **داخل المتصفح** بعد جلب الكتالوج.

هذا مناسب طالما عدد العناصر محدود.

إذا أصبح الكتالوج كبيرًا جدًا، يفضل نقل:

```text
pagination
search
sorting
filtering
```

إلى الباك إند وتعديل عقد `GET /api/catalog` لاحقًا ليقبل Parameters إضافية.

حاليًا لا توجد Pagination من الخادم.

## 18. ما الذي لا يجب وضعه داخل Frontend؟

ممنوع وضع أي سر حقيقي داخل:

```text
index.html
config.js
js/app.js
js/api.js
أي ملف داخل Assets
```

خصوصًا:

```text
Telegram Bot Token
Database URL
Database password
Payment provider secret
Private API key
Webhook secret
Admin secret
JWT signing secret
```

أي قيمة موجودة في الفرونت إند يمكن للمستخدم رؤيتها.

## 19. قواعد أمنية للباك إند

المطور المسؤول عن الخادم يجب أن يعامل جميع البيانات القادمة من الفرونت إند كمدخلات غير موثوقة.

على السيرفر على الأقل:

```text
Verify Telegram initData
Validate all request bodies
Validate category values
Validate item IDs
Load the real price server-side
Validate top-up amount
Apply authorization
Apply rate limiting where needed
Prevent duplicate financial operations
Use idempotency for sensitive payment/order flows when appropriate
Log security-relevant failures
Never return secrets to the frontend
```

إذا كان هناك شراء أو دفع حقيقي، يجب أن تكون **الحالة النهائية للعملية على الخادم** وليس في JavaScript.

## 20. تشغيل المشروع محليًا

لأن المشروع Static Frontend، يفضل تشغيله عبر HTTP Server بسيط بدل فتح `index.html` مباشرة عبر `file://`.

مثال باستخدام Python إن كان متوفرًا:

```bash
python -m http.server 8080
```

ثم:

```text
http://localhost:8080/
```

أو يمكن استخدام أي static server آخر.

بعض خصائص Telegram WebApp الحقيقية لن تكون متاحة عند الفتح في متصفح عادي، لأن `Telegram.WebApp.initData` الحقيقي يأتي عند فتح التطبيق داخل Telegram.

---

## 21. النشر

الفرونت إند يمكن نشره على أي Static Hosting يدعم HTTPS.

متطلبات Telegram Mini App الأساسية من جهة الاستضافة:

```text
HTTPS
ملفات Static قابلة للوصول
index.html كنقطة دخول
الوصول إلى Backend API عبر HTTPS
CORS مضبوط بشكل صحيح إذا كان النطاق مختلفًا
```

لا يحتاج هذا الفرونت إند Node.js أو قاعدة بيانات ليتم عرضه بحد ذاته.

---

## 22. نقطة الدخول القديمة index.htm

`index.htm` موجود فقط للتوافق مع الروابط أو إعدادات استضافة قديمة كانت تشير إليه.

هو يحول إلى:

```text
./index.html
```

مع المحافظة على Query String وHash.

أي تطوير جديد يجب أن يعتبر `index.html` نقطة الدخول الأساسية.

## 23. تعديل التصميم مقابل تعديل التكامل

للحفاظ على فصل واضح بين الفريقين:

| المطلوب | الملف الأساسي |
|---|---|
| ألوان، مسافات، أحجام، Responsive UI | `css/styles.css` |
| إضافة أو تعديل عناصر الصفحة | `index.html` |
| تفاعل المستخدم وعرض البيانات | `js/app.js` |
| تغيير طريقة الاتصال بالباك إند | `js/api.js` |
| تغيير الدومين أو مسارات API | `config.js` |
| صور وأيقونات | `Assets/` |

مطور الباك إند غالبًا **لا يحتاج إلى تعديل CSS أو HTML** حتى يربط النظام.

## 24. Checklist للمطور المستلم

قبل اعتبار التكامل جاهزًا للإنتاج، تحقق من الآتي:

- `apiBaseUrl` يشير إلى Backend HTTPS الصحيح.
- `demoMode` أصبح `false`.
- `GET /api/bootstrap` يعمل لمستخدم Telegram موثق.
- جميع فئات `GET /api/catalog` الأربع تعمل.
- `POST /api/orders` يعيد التحقق من العنصر والسعر على السيرفر.
- `POST /api/wallet/topup` يتحقق من المبلغ على السيرفر.
- `X-Telegram-Init-Data` يتم التحقق منه وليس مجرد قراءته.
- CORS يسمح بدومين الواجهة والهيدر المخصص.
- لا توجد Secrets في ملفات الفرونت إند.
- حالات `401`, `403`, `404`, `409`, `429` و`500` تمت تجربتها.
- عمليات الدفع أو الشراء الحساسة لديها حماية مناسبة من التكرار.
- تم اختبار التطبيق من داخل Telegram وليس المتصفح فقط.

## 25. الخلاصة للمطور القادم

الواجهة جاهزة من ناحية التصميم والتفاعلات الأساسية.

لربطها فعليًا لا تعيد بناء الواجهة ولا تنقل منطق السيرفر إلى JavaScript.

ابدأ من:

```text
config.js
js/api.js
README.md
```

ثم نفذ على الخادم:

```text
/api/bootstrap
/api/catalog
/api/orders
/api/wallet/topup
```

واجعل مصدر الحقيقة دائمًا هو الباك إند.

إذا احتاج الـ Backend إلى تغيير شكل البيانات أو إضافة تدفق جديد، يفضل تعديل عقد الـ API أولًا ثم إجراء أقل تغيير ممكن داخل `js/api.js` و`js/app.js` بدل خلط منطق الخادم مع واجهة المستخدم.

## 26. الصفحات الواجهة المضافة حديثًا

تمت إضافة صفحتين داخل الفرونت إند كواجهات جاهزة فقط، ولا يوجد لهما Backend حتى الآن:

### `#add-product` — أضف منتج

تحتوي على:

- واجهة تعريف لعرض المنتج في سوقي.
- زر `إضافة منتج جديد`.
- زر `إدارة منتجاتي`.
- خطوات شرح إضافة المنتج.
- تنبيه بأن إثباتات الملكية خاصة بالإدارة.

الأزرار في هذه الصفحة **واجهة فقط** حاليًا. لا تنشئ منتجًا ولا تحفظ بيانات ولا ترسل أي API request.

### `#escrow` — الوساطة

تحتوي على:

- شرح آلية الوساطة.
- الرسوم والمهل.
- طرق الدفع والتوثيق.
- الوسطاء المتاحين.
- سجل وساطة تجريبي.
- حالات السجل والفلاتر البصرية.
- بطاقة عملية تجريبية `DEAL-1003`.
- ملاحظات وإخلاء مسؤولية.

جميع بيانات الوساطة المعروضة ثابتة داخل الفرونت إند لأغراض التصميم فقط. لا يوجد حاليًا API للوساطة، ولا يتم إنشاء صفقة أو نزاع أو تغيير حالة من هذه الصفحة.

### شريط التنقل السفلي

الترتيب الحالي:

```text
السوق
طلباتي
أضف منتج
الوساطة
المخزن
```

- `السوق` يفتح `#market`.
- `أضف منتج` يفتح `#add-product`.
- `الوساطة` يفتح `#escrow`.
- داخل صفحة الوساطة، زر `اختر منتجًا وابدأ طلبك` يرجع المستخدم إلى شاشة السوق الرئيسية `#market`.
- زر `سجل عملياتي` ينقل المستخدم داخل نفس الصفحة مباشرة إلى قسم `سجل الوساطة الخاص بك` بتمرير سلس.
- `طلباتي` و`المخزن` ما زالا أزرار واجهة فقط في هذه المرحلة.

### `#account` — حسابي

الضغط على صورة المستخدم في أعلى شاشة السوق يفتح صفحة `حسابي`.

الصفحة تحتوي على:

- صورة المستخدم واسم Telegram إن كانت بيانات WebApp متاحة، مع بيانات معاينة كـ fallback.
- معرف بصيغة `USR-<telegram_user_id>` عندما يكون معرف Telegram متاحًا.
- زر `تعديل الاسم` كواجهة فقط.
- إحصائيات المنتجات والصفقات المكتملة والتقييم كبيانات عرض فقط حاليًا.
- قائمة الحساب: المحفظة، منتجاتي، المفضلة، الإعلان، الإحالة والأرباح، تجارب العملاء، VIP، دليل الاستخدام، الدعم والشكاوى، وتغيير المظهر.
- بطاقة `شروط المتجر` وحالة الموافقة الظاهرة.

سهم الرجوع في أعلى صفحة الحساب يعيد المستخدم دائمًا إلى شاشة السوق الرئيسية `#market`.

جميع عناصر قائمة الحساب الداخلية **واجهة فقط** في هذه المرحلة ولا ترسل API requests.

إذا تم بناء Backend لهذه الصفحات لاحقًا، يجب إضافة العقود الجديدة إلى `js/api.js` و`config.js` وتوثيقها هنا قبل ربطها بمنطق الواجهة.

### Mobile-first layout contract

صفحات `#add-product` و`#escrow` مصممة أساسًا للهاتف، وليس كصفحات Desktop مصغرة.

القواعد الحالية:

- عرض المحتوى المرئي مستهدف أساسًا لشاشات تقريبًا `320px–480px`.
- لا يسمح للصفحات الثانوية بإنشاء Horizontal overflow.
- كل البطاقات والنصوص تستخدم `max-width: 100%` و`min-width: 0` حتى يلتف النص داخل عرض الهاتف بدل قصه.
- شريط الحالات في سجل الوساطة فقط هو الذي يسمح بتمرير أفقي داخلي عند الحاجة.
- شريط التنقل السفلي ثابت، لذلك تترك الصفحات مساحة سفلية إضافية حتى لا يغطي آخر المحتوى.
- أزرار Hero في صفحة الوساطة تظهر جنبًا إلى جنب على الهواتف العادية وتتحول تلقائيًا إلى عمود واحد على الشاشات شديدة الضيق.
- الحد الأقصى لحاوية الصفحات الثانوية `480px` للمحافظة على شكل تطبيق الهاتف حتى عند فتحه داخل نافذة أوسع.
